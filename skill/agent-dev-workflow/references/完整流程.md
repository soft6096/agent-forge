# agent-dev-workflow 完整流程

> 仅在入口分诊判定为「完整流程」时读取。轻量模式与短路不需要本文件。
> 每一步产出后必须停下等确认，禁止连续执行到下一步。

---

## 0.0 agent 项目初始化

从零起项目或首次接入规范时执行，产物 `0.0-agent项目初始化.md`。11 项硬检查，缺一项即为未完成：

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 模型凭据 | 走环境变量或密钥管理，禁止进代码与仓库；日志不得打印密钥 |
| 2 | 模型配置外部化 | 模型名、温度、最大输出长度在配置文件，不硬编码 |
| 3 | 默认超时 | 单次模型调用、单次工具调用、单任务总时长三处都要有 |
| 4 | 步数上限 | 主循环必须有最大步数，且是可配置常量 |
| 5 | 成本上限 | 单任务 token 或金额上限，超限行为明确（降级或中断） |
| 6 | 日志基线 | 会话 id、trace id、步序号、tool 名、token 用量、耗时、结果码 |
| 7 | 提示词外置 | 系统提示词与工具描述放独立文件，带版本标识 |
| 8 | 评测开关 | 存在可运行的评测入口，未接评测集时至少能跑冒烟用例 |
| 9 | 降级路径 | 模型不可用、工具超时、检索无命中的兜底行为各是什么 |
| 10 | 安全开关 | 高危工具的人工确认开关存在且默认开启 |
| 11 | 依赖版本 | 框架与 SDK 版本锁定，写明升级策略 |

确认闸门：11 项逐项给证据（文件:行号），缺项列清单问用户是否补齐。

**与 6.1 核对项的对应**（0.0 建立基线，6.1 交付前复核，同一件事不重复判定）：

| 0.0 检查项 | 对应核对项 | 说明 |
|---|---|---|
| 1 模型凭据 | 无 | 脚本不判密钥，手工确认未进代码与日志 |
| 2 模型配置外部化 | 9~10 | 核对项只判"是否外置 + 有版本"，配置项齐全需人工 |
| 3 默认超时（三处） | 2 | 核对项判有无超时，三处齐全需人工 |
| 4 步数上限 | 1 | 一致 |
| 5 成本上限 | 24 | 一致 |
| 6 日志基线 | 22~23 | 核对项判字段存在，字段值正确性需人工 |
| 7 提示词外置 | 9~10 | 一致 |
| 8 评测开关 | 19~20 | 一致 |
| 9 降级路径 | 无 | 语义项，人工 |
| 10 安全开关 | 26 | 一致 |
| 11 依赖版本 | 无 | 手工核对锁文件 |

6.1 复核时直接引用 0.0 的已有证据并注明「沿用 0.0」，只对新增与变更部分重新取证。

## 0.5 存量 agent 扫描

改造既有 agent 时执行，产物 `0.5-存量agent现状.md`。四个维度：

1. **调用点清单**：所有模型调用位置、封装层次、是否有统一入口
2. **提示词散落位置**：在代码里硬编码的有几处、在配置文件的有几处、是否有版本
3. **工具清单**：现有工具、schema 是否完整、副作用是否分级、是否接 MCP
4. **可观测现状**：有哪些日志字段、有没有 trace、token 是否计量、有没有评测集

扫描后必须给出一个决策闸门，三选一并等用户拍板：

- 全量改造（成本高，适合准备长期迭代）
- 增量对齐（新代码按新规范，旧代码不动）
- 只修当前问题（不引入规范，仅解决本次需求）

未选择不得进入 1.1。

## 1.1 能力清单

产物 `1.1-能力清单.md`。这是全流程最容易被跳过、也最容易埋雷的一步。

必填四段：

0. **需求原文**：逐条**原样摘录**并给 R 编号、注明来源（需求文档路径 / 对话日期 / 纪要），不改写不概括。跨会话接手时，这是唯一能复核"有没有漏需求"的依据；只做映射不粘原文视为未完成
1. **正向能力**：这个 agent 要完成哪些任务，每条一句、可观测
2. **负向边界**：明确不做的事（越权操作、超范围问答、非本领域咨询、无法确认时该拒答），至少三条
3. **成功判据**：每条正向能力对应一句"什么算完成"，必须可判定，不能写"体验好"

覆盖核对：需求按 R 编号逐条映射到正向能力或负向边界，不允许静默消失的条目。

闸门：人确认后才进 1.2。能力清单变更必须回退到此步重走。

## 1.2 失败模式清单

产物 `1.2-失败模式清单.md`。按六类逐条列，每条挂到规范技能，编码时按此对照：

| 类别 | 典型表现 | 挂载规范 |
|---|---|---|
| 幻觉 | 编造事实、编造工具返回、编造引用 | agent-eval-standards（对抗集）+ agent-rag-standards（拒答） |
| 串工具 | 选错工具、参数张冠李戴、多工具结果混用 | agent-tool-standards |
| 死循环 | 反复调同一工具、无限重试、不收敛 | agent-core-standards |
| 越权 | 未确认就执行高危操作、跨租户取数、越界写 | agent-safety-standards |
| 成本失控 | 上下文无限膨胀、重复调用、长尾任务烧钱 | agent-ops-standards + agent-context-memory-standards |
| 上下文溢出 | 历史撑爆窗口、关键约束被裁掉、指令失效 | agent-context-memory-standards |

上表挂载的规范技能均已落地，按各自的加载矩阵精确读子文件；不要用 `check-agent-standards` 的编号项代替它们——核对项只是交付前的机器兜底，不提供设计口径。

每条失败模式必须写：触发条件、预期行为、如何观测、对应评测样本（可留待 2.1 补）。

闸门：人确认后才进 2.1。

## 2.1 评测口径与数据集（强制前置）

产物 `2.1-评测口径与数据集.md`。**本步未确认，禁止进入 5.1。**

必填六项：

1. **数据集分层**
   - 冒烟集：5~15 条，覆盖主路径，每次改动必跑
   - 回归集：覆盖历史失败样本，只增不删
   - 黄金集：人工确认过正确答案，用于版本对比
   - 对抗集：注入、诱导、边界、越权尝试
2. **样本编写规范**：输入、上下文前提、期望结果、判定方式、难度标注、来源（真实/构造）
3. **指标口径**：任务通过率、工具选择正确率、参数正确率、平均步数、平均 token、P95 时延、成本
4. **判定方式**：精确匹配、规则断言、模型裁判。用模型裁判必须写明：裁判模型、评分 rubric、与人工标注的一致性抽检比例、已知偏差
5. **回归基线**：以何版本为基线、允许下降幅度、哪些指标是硬门槛
6. **上线门禁**：哪几项达标才可交付，谁签字

反模式（出现即打回）：

- 用"让另一个模型看一眼"代替规则断言，且不做一致性校验
- 指标只有"准确率"一个，没有成本与时延
- 评测集全部由写码的 agent 自己生成，没有人工确认过的样本
- 没有回归集，只有一次性验收

闸门：人确认后才进 3.1。

## 3.1 agent 架构方案

产物 `3.1-agent架构方案.md`。按功能项一份，必含六段：

1. **循环形态**：单轮 / 工具循环 / 规划-执行 / 多 agent 协作；选择理由与放弃理由
2. **状态机**：阶段划分、状态流转、每阶段的退出条件
3. **上下文预算表**：系统提示词 / 工具描述 / 历史 / 检索片段 / 输出预留，各占多少 token，溢出时先裁谁
4. **记忆策略**：会话内保留什么、跨会话沉淀什么、写入判据、遗忘规则
5. **工具清单**：引用 3.2 的契约，此处只列名称与用途
6. **降级路径**：模型失败 / 工具失败 / 检索无命中 / 超预算 各降级到什么行为

必备章节：验收场景（对应 2.1 的哪几条样本）。

闸门：人确认后才进 3.2。

## 3.2 工具清单与契约

产物 `3.2-工具清单与契约.md`。每个工具一张卡：

| 字段 | 要求 |
|---|---|
| 名称 | 动词+名词，一个工具一件事 |
| 描述 | 模型据此选择工具，必须写清"什么时候该用/不该用" |
| 参数 | 类型、必填、约束、示例、枚举取值范围 |
| 副作用等级 | 只读 / 写 / 高危 |
| 幂等 | 写类工具必须有幂等键与去重窗口 |
| 权限 | 所需角色、租户隔离方式 |
| 错误语义 | 返回给模型的错误结构，必须可读、可自我修正 |
| 超时 | 单次超时与是否可重试 |
| 来源 | 本地实现 / MCP / 内部服务 |

另需一段：工具总数与选择策略（超过 15 个必须写明检索式选择或分组策略）。

闸门：人确认后才进 4.1。

## 4.1 任务拆解

产物 `4.1-任务拆解.md`。Phase 划分固定：

- Phase 0：基础设施（日志、trace、成本计量、超时、开关）
- Phase 0.5：公共组件（模型调用封装、工具注册器、上下文组装器）
- Phase 1：**评测集建设**（独立 Phase，不得并入编码）
- Phase 2：核心链路（骨架与主循环）
- Phase 3：工具实现
- Phase 4：记忆与检索（如涉及）
- Phase 5：安全与兜底
- Phase 6：评测执行与调优

每个任务写：输入、输出、验收标准（可机械判定优先）、依赖、预估工作量。

闸门：人确认后才进 5.1。

## 5.1 编码

按 4.1 顺序实现，编码完成即停，不自行推进到 6.1。

编码期间必须遵守：

- 提示词外置、带版本
- 每个工具的错误返回按 3.2 的错误语义实现
- 所有外部输入与指令分离（安全兜底）
- 每步记录 token 用量与耗时
- 主循环有步数上限与终止条件

产出 `5.1-编码指令.md` 记录：改了哪些文件、每个文件对应哪个任务、遗留项。

## 6.1 规范核对

加载 `check-agent-standards`，先跑脚本，再人工判定语义项。

- 报告逐项附「文件:行号」证据
- 未通过项列待确认清单，与用户确认后补齐
- **修复后必须用同一命令重跑脚本复核**，结果登记进 6.1 报告的「复核记录」段；只有最后一轮复核通过才可进 7.1
- 报告获用户确认后才进 7.1

禁止：写码的 agent 自己写"已全部符合"；无证据的通过标记。

---

## 7.1 评测与覆盖

按 2.1 口径执行，产物 `7.1-评测报告与需求覆盖.md`。

必含：

1. 数据集各层通过率与基线对比（涨/跌/持平 + 幅度）
2. 失败样本逐条归因（归到 1.2 的哪类失败模式）
3. 成本与时延数据（与基线对比）
4. 需求逐条覆盖：按 1.1 的 R 编号逐条给结论（对应哪些代码、哪些样本），不允许按能力合并后把未覆盖需求藏起来
5. 未覆盖项与风险声明

结论形态是统计式的，不允许写成"功能已实现，效果良好"。

闸门：人确认后交付；未达标则回到 4.1 或 3.1，不允许只调提示词硬凑指标而不记录。
