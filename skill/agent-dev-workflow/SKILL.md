# Agent 开发完整流程（需求 → 评测交付）

## 闸门 · 入口分诊（先于一切）

**任何 agent 相关请求进来，先做这一步，再决定要不要读 `references/完整流程.md`。** 回答第一句固定写判档结论，例如：

> 判档：完整流程（依据：新建 agent + 涉及工具与检索 + 需要评测口径）

判档行缺失 = 入场未完成；用户看到依据不对可直接改判，立即改道、不辩解。

### 判据（量化，不靠感觉）

**轻量模式**（下列全部满足）：

- 已有 agent，改动只在提示词文本、模型参数、阈值、单个工具实现细节
- 不改工具契约（schema 不变）、不改上下文预算表、不改评测集
- 不新增能力边界，有明确可复现现象

**完整流程**（任一命中）：

- 新建 agent 项目 / 新增一条 agent 主链路
- 新增或修改工具契约、记忆策略、检索链路、上下文预算表
- 命中新的失败模式，需要改架构
- 需要对外承诺效果（上线、交付、给客户演示）
- 已有产物需要升版本或跨模块同步

**判不清 → 必须问用户**，一次列清两条路 + 【AI 推荐】+ 理由，禁止"先按大的跑反正不会错"，禁止"先改着看"。

### 小改动短路

已指明改哪个文件、哪段提示词、改成什么 → 直接改 → 复现验证 → 四行交付（改动 / 根因 / 影响面 / 验证结果）。不落产物，但仍要过 `check-agent-standards` 的相关项（提示词外置、超时、日志字段）。

## 核心原则（五道防线）

1. **评测口径前置** — 2.1 必须先于 5.1。agent 的输出是分布式的、非确定的，"改完感觉变好了"不是验收依据。没有评测集就不许进编码。
2. **能力清单收负向边界** — 1.1 必须写清"不做什么"。agent 项目失败多为边界失控，而非功能缺失。
3. **失败模式先立** — 1.2 把幻觉、串工具、死循环、越权、成本失控、上下文溢出逐条挂到规范技能上，编码时才有的可对。
4. **角色分离** — 评测由独立步骤或独立 runner 产出，写码的 agent 不自评通过率。
5. **收敛兜底** — 交付前跑 `check-agent-standards` 机械扫描，禁止凭记忆答通过。

## 中间产物落盘规则

- 根目录：项目内 `docs/`，按模块与版本分目录，形如 `docs/<模块>-v<版本>-<时间戳>/`
- 文件名以编号开头，编号与步骤一一对应，不得自创编号
- 产物 md 格式统一按 `templates/通用-中间产物-MD样式规范.md`
- 每个模块目录伴随一份 `通用-模块进度与断点.md`，跨会话接手先跑 /agent-progress，禁止从 1.1 重跑

## 三条硬边界

1. **没有 2.1 不许编码**。评测口径未定就写代码，等于把"验收"变成事后自证。
2. **没有 3.2 不许实现工具**。工具契约先定 schema 与副作用等级，代码只是填充。
3. **6.1 未通过不许进 7.1**。核对报告与评测报告是两个独立结论，不得合并成一句"都挺好"。

## 与其它技能的分工

- 只改提示词/参数/单点实现 → 本技能轻量模式，不落产物
- 任何 agent 代码写完 → 一律过 `check-agent-standards`
- 写技能本身（SKILL.md、触发词、分发）→ `agent-skill-authoring`，不在本流程内
- 技能装不上/改了没生效 → `agent-forge-source-law`
