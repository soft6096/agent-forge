# 02 裁剪、压缩与降级

## 一、三种裁剪策略（至少选一种，写明选哪个）

| 策略 | 做法 | 适用 | 代价 |
|---|---|---|---|
| 滑动窗口 | 只留最近 N 轮 / K 条 | 短任务、客服问答 | 早期约束会丢 |
| 滚动摘要 | 超过阈值时把最旧一段压成摘要 | 长对话 | 多一次模型调用，可能失真 |
| 关键事件保留 | 结构化提取"已确认事实"单独存 | 任务型 agent | 需要定义事件 schema |

推荐组合：**关键事件 + 滚动摘要 + 原文滑窗**（三层），而不是只做滑窗。

## 二、摘要怎么压（丢什么、留什么）

必须保留（丢了会出事）：

- 用户明确表达的约束与禁止项（"不要给我打电话"）
- 已确认的事实与数值（订单号、金额、日期、地址）
- 已执行过的写操作（避免重复执行）
- 未解决的待确认项

可以丢：

- 寒暄与确认性对话（"好的""嗯"）
- 已被推翻的中间结论
- 重复的检索原文（保留摘要与来源即可）

摘要本身要求：

- 用固定模板输出（事实 / 约束 / 待确认 / 已执行），便于机器读
- 摘要长度不超过被压缩原文的 20%
- 摘要带版本或时间戳，注明覆盖到第几轮
- **摘要不得改写数值**：金额、单号、日期原样保留

## 三、触发时机

- 达到预算 70%~80% 触发压缩（配置项 `compress_at`）
- 不要在报错后补救：报错时已经没有空间做压缩了
- 压缩后重新计算占用，若仍超则继续压缩下一段历史
- 连续压缩两次仍不降，说明单条输入或单条检索片段过大 → 走降级

## 四、降级阶梯（固定顺序，禁止跳级）

```
1. 裁检索片段：按相似度从低到高丢，保留至少 1 条（否则走拒答分支）
2. 压历史：摘要化最旧的一段
3. 瘦工具描述：切到检索式工具选择，只留当前需要的
4. 缩短输出预留？——禁止。输出预留不可压缩
5. 仍超限 → 明确告知用户"上下文不足，请缩短输入或分多次提问"，并记录事件
```

禁止行为：

- 静默截断（用户与日志都不知道内容被切了）
- 从中间截断单条消息（一半的 JSON、一半的句子）
- 压缩输出预留去换输入空间

## 五、可观测

每次裁剪 / 压缩必须落一条日志，字段至少：

| 字段 | 说明 |
|---|---|
| step | 第几步 |
| strategy | window / summary / event / retrieval_trim |
| before_tokens / after_tokens | 前后占用 |
| dropped_items | 丢弃条数（按段统计） |
| degraded | 是否走到降级阶梯，走到哪一级 |

没有这些字段，事后无法判断"这次回答差是不是因为把关键约束裁掉了"。

## 六、自查

- [ ] 至少一种裁剪策略，且写清选型理由
- [ ] 摘要保留约束、事实、已执行动作、待确认项
- [ ] 摘要不改写数值，带时间戳与覆盖范围
- [ ] 压缩在 70%~80% 触发，不靠报错兜底
- [ ] 降级按阶梯执行，输出预留不可压缩
- [ ] 裁剪 / 压缩有日志字段（前后 token、丢弃条数、降级级别）
- [ ] 无静默截断、无中间截断单条消息
