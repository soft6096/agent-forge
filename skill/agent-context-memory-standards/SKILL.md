# Agent 上下文与记忆规范

## 定位

上下文是 agent 最贵的资源，也是最容易失控的地方：历史只增不减、检索片段无上限塞入、关键约束被裁掉导致指令失效。记忆则是上下文的时间维度——**什么该沉淀、什么必须丢弃，和"这一轮给模型看什么"是同一张表的两端**，拆开必然出现两份冲突口径。

## 八条硬规则（可核对）

1. **必须有预算表**：系统提示词 / 工具描述 / 历史 / 检索片段 / 输出预留五段各有 token 配额，加总不超窗口，且是配置不是魔数
2. **输出必须预留**：至少按最大输出长度的 1.5 倍预留，禁止把窗口占满后再让模型说话
3. **不可变段放最前**：身份、硬约束、禁止项在提示词前部且不被裁剪，历史与检索片段永远排在后面
4. **历史必须有裁剪策略**：滑动窗口 / 摘要压缩 / 关键事件保留，三者至少一种，禁止只 append
5. **压缩要有触发阈值**：达到预算的 70%~80% 触发，而不是等报错
6. **超限必须有降级路径**：先裁检索片段 → 再压历史 → 最后明确告知"上下文不足，请缩短输入"，不允许静默截断
7. **记忆写入必须有判据函数**：不是所有交互都值得记；判据要能回答"下次什么情况下会用到"
8. **记忆与上下文隔离租户**：记忆键含租户，敏感字段（证件、卡号、口令、密钥）一律禁写

## 三条反例（出现即返工）

- 每轮把所有历史消息原样拼接，靠模型窗口足够大"应该没问题"
- 检索命中 30 条全部塞进上下文，没有条数与 token 上限
- 把用户身份证号、手机号整段写进长期记忆，只因为有"记忆"这个功能

## 交付前

上下文与记忆相关代码写完，过 `check-agent-standards` 的「上下文」与「记忆」类核对项（第 11~15 项：token 预算、裁剪压缩、输出预留、记忆写入判据、敏感字段禁写），每项附文件行号证据；"预算表是否加总合理""判据是否真能回答下次何时用"属语义项，人工判定。
