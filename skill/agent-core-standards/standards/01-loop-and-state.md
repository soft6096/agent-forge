# 01 主循环与状态机

## 一、循环形态选择

| 形态 | 适用 | 不适用 | 成本特征 |
|---|---|---|---|
| 单轮 | 输入输出一次成型，无工具 | 需要外部事实、需要多步操作 | 最低 |
| 工具循环 | 需要查资料、算数、调接口 | 步骤间有强依赖编排 | 中，随步数线性增长 |
| 规划-执行 | 任务可先分解再逐步执行 | 高度依赖实时反馈 | 高，多一次规划调用 |
| 多 agent 协作 | 子任务差异大、可并行 | 任务本身简单 | 最高，且难调试 |

选择规则：

1. 能用工具循环解决就不要上规划-执行
2. 能用规划-执行解决就不要上多 agent（多 agent 的失败归因成本极高）
3. 选择与放弃都要在同一份方案里写明理由，禁止默认"先上多 agent 显得先进"

## 二、主循环骨架

固定五段，每段职责单一，禁止合并：

```
初始化状态
循环（每次迭代 = 一步）：
  1. 组装本轮上下文（agent-context-memory-standards 规划中，暂按 check 第 11~13 项：预算、裁剪、输出预留）
  2. 调模型，记录 token 与耗时
  3. 解析输出：工具调用 / 最终答案 / 异常
  4. 若为工具调用：校验 → 权限 → 执行 → 回填结果
  5. 检查终止条件
收尾：落状态快照、写审计、计费
```

硬要求：

- 每步开始时递增步序号，写进日志与 trace
- 每步结束前检查终止条件，不允许在步中间 return 造成状态不一致
- 模型返回的原始内容必须原样落日志（脱敏后），便于复盘

## 三、状态机

状态必须显式建模，不允许用布尔组合代替。

| 要求 | 说明 |
|---|---|
| 阶段可枚举 | 枚举类型或常量集，禁止散落字符串 |
| 流转有守卫 | 每个流转写清进入条件，非法流转直接报错，不静默 |
| 每阶段有退出条件 | 超时、步数、外部信号都算退出条件 |
| 状态可序列化 | 能完整落 JSON，含步序号、已用工具、累积 token、待确认项 |
| 状态不可变更新 | 每步产出新状态，便于对比与回放 |

反例：

```
// 反例：用三个布尔表示状态，组合爆炸且无法回放
boolean callingTool, hasResult, finished;
```

## 四、终止条件（五类必须齐全）

| 类型 | 触发 | 返回值约定 |
|---|---|---|
| 正常完成 | 模型给出最终答案 | success + 答案 |
| 步数耗尽 | 达到最大步数 | exhausted + 已完成部分 + 建议 |
| 预算耗尽 | token 或成本超限 | budget_exceeded + 已完成部分 |
| 用户中断 | 收到取消信号 | cancelled + 可恢复快照 |
| 安全拦截 | 命中高危或注入规则 | blocked + 拦截原因码 |

实现要求：

- 五类都要有独立的返回结构，禁止统一 `error`
- 每种终止都要写一条日志，含触发时的步序号与累计用量
- 「步数耗尽」必须能回答"卡在哪一步、在等什么"

## 五、步数上限怎么定

| 任务复杂度 | 建议上限 | 说明 |
|---|---|---|
| 单工具查询 | 5 | 一次调用 + 一次总结 |
| 多工具串联 | 10~15 | 每个工具预留 2 步 |
| 规划-执行 | 20~30 | 含规划与每步校验 |
| 开放式任务 | 需人工确认 | 无上限的开放式任务不建议上线 |

上限值必须配置化，且与成本上限联动：步数上限 × 单片均 token ≤ 成本上限。

## 六、自查

- [ ] 主循环五段职责清晰，无合并
- [ ] 状态为显式枚举，可序列化
- [ ] 五类终止条件都有独立返回结构
- [ ] 步数上限可配置且与成本上限联动
- [ ] 每步有步序号日志
