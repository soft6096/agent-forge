# 02 召回参数、重排与查询改写

## 一、召回参数

| 参数 | 起点 | 调法 |
|---|---|---|
| top_k（初召） | 10~20 | 只用于喂重排，不直接进上下文 |
| top_n（进上下文） | 3~8 | 受上下文预算约束 |
| 相似度阈值 | 用评测集定，先跑分布 | 低于阈值即视为无命中 |
| 每文档最多条数 | 2~3 | 防单文档霸屏 |

阈值怎么定（不要拍脑袋）：

1. 用评测集跑出一批 query 的 top-1 分数分布
2. 取"正确命中"的分数下界与"错误命中"的分数上界，阈值落在两者之间
3. 上线后按无命中率回归调整：无命中率突升说明阈值过高，答案变差说明过低

**只有 top_k 没有阈值的检索等于没有拒答能力。**

## 二、查询改写

| 手段 | 何时用 | 风险 |
|---|---|---|
| 同义扩展 | 用户用词与文档用词不一致 | 引入无关词，召回噪音上升 |
| 抽取实体 + 关键词 | 问题里含单号、产品型号 | 抽取错导致偏题 |
| 多轮改写（带历史） | 追问场景（"那它呢"） | 改写引入历史里的旧约束 |
| 拆分子问题 | 复合问题 | 子问题漏召回 |
| HyDE（假设答案再检索） | 短问题、术语多 | 假设答案错则整体偏 |

硬约束：

- 改写**只允许扩展或澄清，不允许新增约束**（如用户没提时间，改写不能加"2025 年"）
- 改写前后都要可对比（记录原 query、改写 query、各自召回结果）
- 改写结果为空或异常时**回退原 query**，不要直接检索空串

## 三、多路召回与融合

- 常见组合：向量召回 + 关键词（BM25）召回 + 结构化筛选（时间 / 类别 / 租户）
- 融合方式二选一，写明选哪个：
  - **加权分数融合**：各路分数归一化后加权（不同来源分数尺度不同，必须先归一化）
  - **RRF（倒数排名融合）**：只依赖排名，不需要分数可比，工程上更稳
- 融合后必须**去重**（同一 chunk 被多路命中时按 chunk_id 合并，保留最高分与来源）
- 融合权重进配置，调整需附召回评测对比

## 四、重排

| 何时需要 | 说明 |
|---|---|
| 初召 20 条、只用 5 条 | 重排能显著提升进上下文的质量 |
| 查询短、语义模糊 | 向量相似度不足 |
| 文档风格差异大 | 需要交叉编码器判相关性 |

要求：

- 重排模型也要记录版本，换版本需重跑评测
- 重排有超时（如 300~800ms），超时**降级为原顺序**而不是失败
- 重排分数与初召分数都记录，便于分析"是不是重排把对的排掉了"

## 五、召回结果的结构约定

每条召回项至少带：

```
{ chunk_id, doc_id, text, score, source: "vector|bm25|filter",
  section_path, offset, updated_at }
```

缺 `section_path` 无法生成可读引用；缺 `score` 无法做阈值与调试。

## 六、自查

- [ ] top_k（初召）与 top_n（进上下文）分开设置
- [ ] 相似度阈值由评测分布确定，有调整依据
- [ ] 每文档条数上限存在，防单文档霸屏
- [ ] 查询改写不新增约束，有回退原 query 的分支
- [ ] 多路融合方式明确，先归一化或用 RRF，融合后去重
- [ ] 重排有超时且超时降级为原顺序
- [ ] 召回项字段齐全（chunk_id / score / section_path / source / updated_at）
